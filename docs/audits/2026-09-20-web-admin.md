# Web admin console audit (2026-09-20)

Scope: the Cloudflare Worker console in `cloud/` (source, migrations 0001-0005, tests, docs), as deployed at projectors.photogen5000.com. Branch `audit-web` at `4a5f6e6`. Nothing was changed, deployed or run against the live site; every reproduction ran against local `wrangler dev` or the vitest suite (267 tests pass at baseline).

## Summary for the owner

1. Nobody can get in from the outside without a password. Sign-in, sessions, the checks on every form, uploads and the device connections all hold up; no way was found for a stranger to see or control anything.
2. The biggest problem is the "enrollment key". It is one shared secret that sits on every flashed SD card and every flasher laptop. Anyone who has it can take over any projector that is already registered, and from there read the Wyze camera password and the camera tunnel. Fix: hand out a fresh device token on every re-enrollment instead of the old one.
3. Anyone with the editor role can read the Wyze camera account password, even though the Settings page says it is never shown again. The password travels to every projector, and editors can see every projector's token.
4. If you remove someone from the alert email list, they keep access to every live camera page until the tunnel of every device is recreated by hand. The Settings page does not say so.
5. Typing "EST" or "MST" as the timezone is accepted, but those names ignore daylight saving, so every schedule would run an hour off for eight months of the year.
6. Many ordinary mistakes in forms (a duplicate name, a typo in the timezone, an empty password box) answer with a bare page of computer text instead of the form with a message, and everything you typed is lost.
7. A stranger can fill the audit log with junk sign-in attempts of any size, and the audit log cannot be searched or paged, so real actions scroll out of view within weeks.
8. Smaller things: resetting someone's password does not sign them out; two clicks on Reboot reboot the projector twice; a short network blip raises a misleading "no new screenshot" alert; some text is 9px and some grey text is too faint to read; the top menu hides Users and Settings on a tablet-sized window.
9. The deploy and backup instructions understate what a database dump contains and what rotating the session secret destroys (the Wyze and Twilio credentials).
10. Nothing is on fire. Most fixes are small and local; the two design changes (a fresh token on re-enrollment, and who may see device tokens) need a decision from you.

Totals: 0 Critical, 7 High, 24 Medium, 54 Low. Ten further reports were checked and judged to be deliberate, documented design choices; they are listed at the end.

## How this audit was done

Every source file under `cloud/src`, `cloud/public`, `cloud/migrations`, `cloud/test` and the docs was read. Nine independent auditors (web sessions and CSRF; device and operator APIs; uploads and media; secrets and integrations; crons, manifest and schedules; migration 0005 and the device flows; a page-by-page walk as a non-technical owner; tests and docs; the anonymous route matrix) produced 112 reports, merged to 86. Each surviving report was then checked by two further auditors: one told to refute it (re-reading the code and reproducing it with a throwaway vitest file or a request against local `wrangler dev`), one to judge severity, the fix and existing test coverage. A completeness pass covered the checklist items nobody had named and added five targeted checks (per-device command duplicates, Access policy staleness, last-admin races, audit-log reachability, real browser layout at phone, tablet and desktop widths). Reports that did not reproduce, or that turned out to be documented design choices with a harmless trade-off, were dropped. Every finding below was reproduced independently at least twice; "How to reproduce" describes what was actually run.

Severity scale: Critical = an anonymous or low-privilege actor gains control, data is lost, or the fleet stops; High = a real security or correctness defect an authenticated user, a device or normal operation can trigger, or something the owner will hit in ordinary use; Medium = limited blast radius or unusual conditions; Low = hardening, polish, wording.

Line numbers refer to branch `audit-web` at `4a5f6e6`. Paths are relative to the repository root.

#### H1. Anonymous POST /login writes unbounded, never-expiring audit rows: no username length cap, throttle keyed on ip+username so rotating usernames is never limited, and /audit becomes unusable

**Severity:** High (Security). **Where:** `cloud/src/pages/login.js:62`

**What happens:** The login username is not length-limited (login.js:62) and is stored verbatim in audit_log.details for every failed login (login.js:77) and in login_failures (auth.js:251). The throttle (auth.js:238-241) counts WHERE ip AND username, so a caller who varies the username per request is never locked out (12 consecutive failures from one IP all 200); one anonymous session's CSRF token works for every attempt and each burns a 100k-iteration PBKDF2. Rows are as large as the attacker likes (a 200 KB username gave a 200,018-byte details column; D1 allows 2 MB rows) and are kept PIPLAYER_AUDIT_RETENTION_DAYS = 365. Consequences: D1 storage/row-write billing grow without bound (10 GB cap, after which every console write and every device sync that updates last_seen fails); /audit renders details at full length, five such rows made a 1 MB page, the default 200 rows would be 40 MB and the 1000-row link 200 MB, over the Worker's 128 MB memory, so the Audit page 500s and the real trail is pushed out of the 200/1000-row view and the dashboard; the rows flow into scripts/backup.md dumps. No Cloudflare rate-limit rule is configured in the repo.

**How to reproduce:** vitest: 12 anonymous POST /login with username 'u'.repeat(200000)+i, password 'x', cf-connecting-ip 203.0.113.9: all 200 (no 429); audit_log gained 12 login_failed rows with details length 200018; GET /audit?limit=5 as viewer returned a 1,004,199-byte page. Second probe with 100 KB usernames: 12 rows, viewer /audit body > 1.2 MB.

**Fix:** 

1) src/auth.js: add `export const MAX_USERNAME_CHARS = 64;` and `export const LOGIN_IP_MAX_FAILURES = 20;` next to LOGIN_MAX_FAILURES (line 20). In loginLockedFor (line 238-246) drop the username filter from SQL and apply the per-IP ceiling on the same result set:
```js
const rows = await db.all(env,
  "SELECT username, at FROM login_failures WHERE ip = ? AND at > ? ORDER BY at",
  ip || "-", now - seconds);
const mine = rows.filter((r) => r.username === username);
if (mine.length < max && rows.length < LOGIN_IP_MAX_FAILURES) return 0;
const last = rows[rows.length - 1].at;
```
2) src/pages/login.js loginSubmit: after line 62 insert
```js
if (username.length > auth.MAX_USERNAME_CHARS) return loginPage(ctx, "Username too long", 400, false, next);
```
(before loginLockedFor and before any PBKDF2, so the audit and login_failures rows are bounded to 64 chars and the oversized request costs nothing). No change to audit.log(); inputs are capped at the boundary like every other caller. Optionally apply the same 64-char check in pages/users.js usersCreate (line 114) so no legitimate account can ever exceed it.


**Covered by a test today:** no. test/security.test.js "five failed logins in 30 s lock that ip+username for 30 s (429), others unaffected" and test/auth.test.js "throttles after five failures per ip+username" cover only the same-username lock; test/pages_audit.test.js "newest first ... details escaped" covers escaping, not length. Nothing tests a long username, rotating usernames, or a per-IP ceiling.

#### H2. Enrollment key is a skeleton key: re-enrolling any existing device_id hands out that device's live token (and with it the Wyze password, tunnel token, media, and the ability to spoof the device) and renames it

**Severity:** High (Security). **Where:** `cloud/src/api.js:286`

**What happens:** POST /api/enroll with the shared enrollment key and an existing device_id does not mint a new token: it returns the device's current token unchanged (api.js:260, 286) and renames the device to whatever the body carries (api.js:278-283), which also rewrites the derived Wyze camera name and bumps camera_config_version fleet-wide; the audit row does not say a rename happened. The key is a single long-lived secret written to every SD card, fetched by every flasher PC (GET /api/operator/enrollment) and handed to every editor with a p5k token. Device ids are short human names (lobby-1) shown on the Devices page and public as <device_id>-cam CNAMEs, and the enroll throttle counts only wrong keys, so id guessing with the right key is unlimited. One lost or borrowed card, a flasher log or a leaked operator token therefore yields the token of every device in the fleet without touching a Pi. A device token unlocks GET /api/camera-config (the Wyze account email + password in clear, api.js:317-327), the Cloudflare tunnel connector token on every sync (api.js:97, 107-115), all media in the playlist, and lets the holder spoof status, screenshots, camera snapshots and mark commands (a reboot) completed. Rotating the enrollment key afterwards (docs/automation.md 'Rotation') does not revoke harvested device tokens. README.md:212, docs/adding-a-pi.md:59 and automation.md describe re-enrollment as 'same token, same playlist' but never say the key alone retrieves the token; the trade-off is not needed since a re-flashed card has no token anyway.

**How to reproduce:** vitest (three independent probes): device lobby-1 with token tok-lobby-1 and Wyze secrets set; POST /api/enroll {key, device_id:'lobby-1', name:'pwned'} -> 200 {token:'tok-lobby-1'}; device renamed to 'pwned'; GET /api/camera-config/lobby-1 with that token -> {source:'wyze', wyze:{email:'ops@example.com', password:'hunter2!'}}; audit row is {"device_id":"lobby-1","name":"pwned"}.

**Fix:** 

In src/api.js enroll(), replace lines 278-286 so a re-enrollment mints a new token (same pattern as devicesRegenToken, src/pages/devices.js:589) and records the old name:

```
  const token = randomToken(32);
  await db.run(ctx.env, "UPDATE devices SET token = ?, name = ? WHERE id = ?", token, name, row.id);
  if (row.name !== name) await db.bumpCameraConfigVersion(ctx.env); // Wyze camera name may derive from the device name
  await audit.log(ctx, "device_reenrolled", "device", row.id,
    { device_id: deviceId, name, renamed_from: row.name !== name ? row.name : undefined }, null);
  if (!row.tunnel_id && cloudflare.configured(ctx.env)) await cloudflare.tryProvisionDevice(ctx, { id: row.id, device_id: deviceId });
  return json({ device_id: deviceId, token, cms_url: ctx.url.origin });
```
Update the comment at api.js:239-244 ("Re-enrolling an existing device_id issues a NEW token: the re-flashed card works, the old card and anything that learned the old token stop"). Update test/enroll.test.js "re-enrolling keeps the existing token..." to assert again.token !== first.token, row.token === again.token, and that GET /api/sync/hall-2 with first.token now returns 401, and that the audit details carry renamed_from. Update README.md:212-213, ../docs/adding-a-pi.md:59-60 and ../docs/automation.md:46-50 to say a re-flash gets a new token and the old card stops syncing, and that the enrollment key alone can re-enroll any device id, so rotate it whenever a card, a flasher PC or an operator token is lost. Skip "require the current token" (breaks the re-flash case) and skip "rename only on create" (the flasher's name is the operator's intent; renamed_from plus the ip already in audit_log makes it loud).


**Covered by a test today:** test/enroll.test.js "re-enrolling keeps the existing token, updates the name, audits device_reenrolled" asserts the current unsafe behaviour (token: first.token, audit details without renamed_from) and must be flipped. No test covers the key -> token -> /api/camera-config chain; test/camera_config.test.js "device bearer only: no token 401, another device 403, a browser session 401" covers only the bearer check.

#### H3. Any editor (or anyone holding a Pi's SD card) can read the admin-only Wyze account password: device tokens are printed to every editor and /api/camera-config returns the credentials in clear

**Severity:** High (Security). **Where:** `cloud/src/pages/devices.js:494`

**What happens:** The Wyze email, password and API key are entered on the admin-only Settings page, stored AES-GCM encrypted and advertised as 'Stored encrypted; never shown again' (settings.js wyzePanel), 'There is no reveal' (docs/automation.md) and 'Nothing here renders a value' (secrets.js:5). But GET /api/camera-config/{id} (api.js:317-326, cameraConfig at devices.js:184-189) returns the full plaintext account to any device bearer token, and the Devices page prints every device's plaintext token to every editor (devices.js:494 loads them for canEdit, :440 renders <code class="token">). An editor, who cannot open /settings, copies any token from /devices and one curl later holds the owner's whole Wyze account (password, API key), which unlocks every camera and the account itself; the same token lets them impersonate the player (fake sync status, screenshots, command results). A revoked or demoted editor who copied a token once keeps this until every device token is regenerated. The same path exists for anyone who pulls the SD card out of a Pi in a venue. Nothing on Settings or in the docs tells the admin that editors and every Pi can read these values; the page says the opposite. Two admins today, but Users can add editors and the flasher device-code flow issues editor tokens.

**How to reproduce:** vitest (two probes): admin POSTs /settings/wyze with password hunter2!; editor GET /settings is 403 and the admin page never contains the value; editor GET /devices contains <code class="token">tok-probe-a</code>; GET /api/camera-config/probe-a with that bearer returns {wyze:{password:"hunter2!", api_key:...}}.

**Fix:** Two parts, both small. (1) Stop the page lying: in src/pages/settings.js wyzePanel line 109 replace "Stored encrypted; never shown again." with plain English such as "The console never shows these again, but every player receives the full login, so anyone who can install a player (editors, operator tokens, or someone holding a Pi's SD card) can read the password. Use a Wyze account made just for the projector cameras." Mirror that sentence in docs/automation.md next to line 378. (2) If the editor boundary is meant to hold, gate device-token issuance at admin in the three places that grant one: devices.js:494 change canEdit to an isAdmin check (auth.roleRank(user.role) >= auth.roleRank("admin")) for the tokens map so the block at :438-455 disappears for editors; api.js:296 and device_codes.js:175/:182 change "editor" to "admin". Then update roles_csrf.test.js "viewers never see device tokens..." to expect editors not to see them. Do not add a new abstraction or a per-device credential layer for this.

**Covered by a test today:** partly: test/camera_config.test.js "admin only; page shows not set and no values; saving stores encrypted, bumps the version, audits without values" (Settings never renders the value) and "site default = wyze when the account is set, camera name from the pattern; audited once a day" (asserts the device endpoint returns password "new-pass"); test/roles_csrf.test.js "viewers never see device tokens or the install command; editors and admins do" (asserts the current editor exposure). No test covers the editor-to-Wyze-password chain, and none covers operator token -> enrollment key -> enroll -> camera-config.

#### H5. Typing "EST" or "MST" as the site timezone is accepted but silently maps to a zone with no daylight saving, so schedules run an hour off for eight months

**Severity:** High (Correctness). **Where:** `cloud/src/util.js:190`

**What happens:** The timezone is a free-text input with a datalist (settings.js:227-230) and the only check is isValidTimeZone (util.js:190-198), which accepts anything Intl.DateTimeFormat accepts. ICU accepts legacy abbreviations: "PST" resolves to America/Los_Angeles (fine), but "EST" resolves to America/Panama and "MST" to America/Phoenix, fixed-offset zones that never enter daylight time. An east-coast owner who types "EST" gets a settings page that says zone EST, a dashboard clock right in winter, and every schedule rule, the projector auto-power lead time, the nightly update window and the manifest server_time an hour early from March to November. Nothing warns; settings.js:254 just echoes "Zone EST".

**How to reproduce:** POST /settings with timezone=EST -> 303 saved; util.wallClock("EST", 2026-07-01T16:00Z) gives hour 11 zone EST while America/New_York gives hour 12 zone EDT; serverTimeIso("EST", ...) is 2026-07-01T11:00:00-05:00.

**Fix:** 

In cloud/src/util.js, isValidTimeZone (line 190): keep the Intl.DateTimeFormat try/catch, then additionally require the name to be "UTC" or a member of Intl.supportedValuesOf("timeZone"):

```
export function isValidTimeZone(tz) {
  if (typeof tz !== "string" || !tz) return false;
  try {
    new Intl.DateTimeFormat("en-US", { timeZone: tz });
  } catch {
    return false;
  }
  if (tz === "UTC") return true;
  try {
    return Intl.supportedValuesOf("timeZone").includes(tz); // rejects EST/MST/PST etc., which ICU maps to fixed-offset zones
  } catch {
    return true; // runtime without supportedValuesOf: fall back to the Intl check
  }
}
```
That alone fixes settings.js:314 (its only caller) and leaves the datalist as is. Optionally change the 400 text at settings.js:314 to plain English, e.g. "Pick a timezone from the list, for example America/New_York (short names like EST are not accepted)". Do not replace the input with a <select>: "UTC" is the default and is not in supportedValuesOf, so a select would need its own special case, and the datalist already offers the list.


**Covered by a test today:** no (test/pages_settings.test.js "validation: 400 for a bad zone, interval < 15 or non-int, bad duration; nothing saved" only sends Mars/Olympus and ""; a throwaway test file (deleted afterwards) is another auditor's throwaway file, not suite coverage)

```
function errorResponse(ctx, status, detail, headers) {

```

Separate one-attribute polish, each its own line: users.js:52 add `required`; settings.js:160 `type="email" multiple`; settings.js:163 add `pattern="https://.*"`; devices.js:282/310/397 gate the /settings link on ctx.user.role === "admin" the way schedule.js:50 does; setup.js gate(): on GET with a wrong or missing token render the auth card with "This console has not been set up yet. #### H7. Audit log cannot be searched, filtered or paged: human actions fall out of reach within weeks (hours under a login bot)

**Severity:** High (User experience). **Where:** `cloud/src/pages/audit.js:25`

**What happens:** GET /audit runs one query, `SELECT ... #### M1. Open redirect after login: a tab (or newline) in ?next= passes nextPath; browsers resolve the Location to an attacker host, a newline makes login 500 without setting the cookie

**Severity:** Medium (Security). **Where:** `cloud/src/pages/login.js:33`

```js
export function ipBucket(ip) {
```
